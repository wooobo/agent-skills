# 화면전환 / 신전환 프롬프트 라이브러리 (Scene Transition Library)

AI **영상** 생성 프롬프트에 **샷과 샷, 장면과 장면 사이의 전환**을 입힐 때 쓰는 **프롬프트 블록 라이브러리**다. 원리는 자매 스킬 `composition`·`color-grade`·`camera-motion`·`vfx`와 같다: 원하는 전환의 *결과*(어떻게 끊기는지, 겹치는지, 갈라지는지, 변형되는지)를 편집·촬영 용어로 "묘사"한 **~82종의 영어 "전환 블록"** 을, 골라서 프롬프트에 끼워 넣기만 하면 되게 정리한 것이다.

이 스킬의 가치는 "전환 영상을 만든다"가 아니라 **"원하는 전환에 맞는 정확한 전환 블록을 골라, 두 샷 사이의 경계에 올바르게 앉힌다"** 는 데 있다.

## 다른 4개 스킬과의 근본적 차이 — "안"이 아니라 "사이"

`composition`·`color-grade`·`camera-motion`·`vfx`는 전부 **한 샷을 어떻게 찍는가**(구도·색감·무브·효과)를 다룬다. 한 샷의 스택 `<composition><subject+action><vfx><camera-motion><color-grade>` **안**에 블록 하나를 끼워 넣으면 된다.

`scene-transition`은 다르다. **한 샷이 다음 샷으로 어떻게 넘어가는가**를 다룬다. 즉 단일 스택 안의 재료가 아니라, **완결된 두 스택 사이의 경계** 그 자체다:

```
[샷A: 구도+피사체·동작+VFX+무브+색감 전체 스택]  <전환 블록>  [샷B: 구도+피사체·동작+VFX+무브+색감 전체 스택]
```

## 이 스킬이 하는 일 / 안 하는 일

**한다:**
- 사용자가 원하는 전환(하드컷, 디졸브, 와이프, 매치컷, 모프, 줌스루 등)에 맞는 **전환 블록을 골라** 준다.
- 그 블록을 **샷A와 샷B 사이의 올바른 위치·형태로** 끼워 넣어 완성된 프롬프트(또는 워크플로 지시)를 만들어 준다.
- 매치·모프 계열에서는 **무엇을 고정하고 무엇을 바꿀지**(포즈·색·실루엣·구도)까지 짚어준다.

**안 한다 (라이브러리 전용):**
- **영상 생성 호출을 하지 않는다.** `generate_video`를 부르는 건 이 스킬의 영역 밖이다. 실제 생성은 사용자가 직접 하거나 생성 경로가 맡는다.
- **한 샷 안의 카메라 움직임**은 다루지 않는다 → `camera-motion`. **한 샷 안의 효과**도 다루지 않는다 → `vfx`. 이 스킬은 오직 **경계**만 다룬다.

## 삽입 위치 — 세 갈래 적용 방식

전환 블록은 자매 스킬들처럼 "한 프롬프트 안의 한 지점"에 끼우는 게 아니라, **두 개의 생성 잡(job) 경계**에서 아래 세 가지 방식 중 하나로 적용된다:

1. **텍스트 프롬프트 꼬리/머리**: 순수 텍스트 프롬프트라면 샷A 지시문의 **마지막 순간**(꼬리)이나 샷B 지시문의 **첫 순간**(머리)에 전환 블록을 붙인다. 짧고 즉각적인 전환(하드컷, 스매시컷, 플래시컷 등)에 적합.
2. **전환 전용 클립**: 지속시간이 있는 전환(모프, 파티클 오버레이, 필름번, 리퀴드 모프 등)은 샷A·샷B와 별도로 **전환만 담당하는 짧은 클립**을 생성해 그 사이에 끼워 넣는 편이 안정적이다.
3. **start/end 프레임 워크플로**: Kling·Luma·Runway·Seedance 등 첫/끝 프레임을 참조 이미지로 받는 모델이라면, 샷A의 마지막 생성 프레임을 샷B의 시작 참조 이미지로 그대로 넣고, 전환 블록으로 **무엇을 고정하고 무엇을 바꾸는지**만 문구로 명시한다.

어떤 방식을 쓸지는 **사용하는 모델이 무엇을 지원하는지**가 먼저 정해야 한다. 지원 여부를 모르면 사용자에게 확인한다.

## 다섯 가지 대원칙

1. **전환은 '경계' 하나만 묘사한다.** 샷A·샷B 전체 스택을 다시 쓰지 않는다 — 그 사이 이음매만 짧게 얹는다. 구도·색감·무브·효과는 각 샷 쪽 스킬(`composition`/`color-grade`/`camera-motion`/`vfx`)의 몫이다.
2. **컷포인트당 지배적 전환 하나.** `camera-motion`의 "지배적 무브 하나", `vfx`의 "히어로 효과 하나"와 동형이다. 와이프+모프+파티클+플래시를 한 이음매에 겹치면 AI 영상이 결과를 뭉갠다.
3. **무엇을 고정하고 무엇을 바꾸는지 명시한다.** 매치·모프 계열(그래픽 매치 컷, 매치-포즈, 오브젝트 모프 등)은 겹치는 축(포즈/색/실루엣/구도 중 어느 것)을 짚어줘야 이어붙는 느낌이 산다. 안 적으면 AI가 임의로 다시 그려 이음매가 깨진다.
4. **편집 이론 용어가 아니라 그 결과의 시각 묘사를 적는다.** "J컷 넣어줘"는 사람에게는 통해도 T2V/I2V 모델은 모른다. 개념이 아니라 그 개념이 만들어내는 *화면 상태*를 영어 블록으로 번역해서 적는다. (오디오 기반 개념 — J컷/L컷/사운드 브릿지/스팅어 컷 등 — 은 순수 영상 생성 모델에서 시각적으로만 근사되며 완전히 재현되지 않는다는 점을 사용자에게 알린다.)
5. **start/end 프레임 워크플로는 텍스트 전환 문구와 다른 도구다.** 생성 모델의 이미지 입력 슬롯(첫/끝 프레임)을 쓰는 것이므로, 어떤 워크플로를 쓸지 먼저 정하고 그에 맞는 전환을 고른다.

## 워크플로

1. **전환 파악**: 사용자가 원하는 느낌/레퍼런스를 듣는다. 이름을 정확히 안 대도 된다("부드럽게 넘어가줘" → cross dissolve, "화면이 확 바뀌게" → hard cut/smash cut, "눈으로 줌인해서 다음 장면으로" → eye zoom-through, "그림처럼 겹쳐서" → superimpose transition, "장면이 녹아서 다음으로" → liquid/object morph, "빙글 돌면서 넘어가게" → cube spin/spin transition, "화면이 깨지면서" → glass shatter transition, "루프 영상으로" → seamless loop 등으로 매핑).
2. **전환 선택**: 아래 **인덱스**에서 후보를 고른다. 딱 하나가 정석이면 그걸로, 애매하면 2~3개를 제안해 고르게 한다. **컷포인트당 지배적 전환 하나** 원칙을 지킨다.
3. **블록 가져오기**: 해당 전환이 있는 `references/*.md`에서 그 항목의 **전환 블록**(영어)을 가져온다. 🔗 표시가 있는 항목은 `camera-motion`/`vfx`의 기존 블록을 그대로 가져오고, 이 스킬에서는 "전환으로 쓰는 법"만 참고한다.
4. **적용 방식 결정**: 텍스트 꼬리/머리 삽입인지, 전환 전용 클립인지, start/end 프레임 워크플로인지 사용자의 생성 모델·상황에 맞춰 정한다.
5. **삽입 & 고정축 명시**: 매치·모프 계열이면 무엇을 고정(포즈/색/실루엣/구도)하고 무엇을 바꾸는지 문구에 반영한다.
6. **전달**: 완성된 전환 블록(+적용 방식 설명)을 준다. 생성은 사용자/생성 경로에 맡긴다.

## 안 통하는 것 (사용자가 요청해도 피한다)

- **전환 장치 과적재** → 한 컷포인트에 와이프+모프+파티클+플래시를 동시에 걸면 AI 영상이 이음매를 뭉갠다. 지배적 전환 하나만.
- **camera-motion 3종/vfx 12종을 다시 서술** → 이미 있는 블록이다. 새로 쓰지 말고 링크만 걸고, "전환으로 쓰는 법"(타이밍·배치)만 추가한다.
- **매치·모프 계열에서 고정축 미지정** → 포즈/실루엣/색/구도 중 무엇이 겹치는지 안 적으면 AI가 임의로 이어 붙여 매치가 안 보인다.
- **편집 이론 용어를 시각 묘사 없이 그대로 프롬프트에 삽입** → "J컷 처리해줘"는 생성 모델이 못 알아듣는다. 결과로 보이는 시각적 상태로 번역해서 적는다.
- **대응점 없는 두 이미지로 start/end 프레임 인터폴레이션** → 인터폴레이션이 왜곡되거나 실패한다. 포즈·구도·색 중 하나 이상은 공통으로 고정한다.
- **형태 유사성 없는 대상끼리 모프** (예: 사람→자동차) → 중간 프레임이 뭉개진 덩어리로 붕괴한다. 실루엣·비율이 겹치는 대상끼리 연결한다.
- **퍼펙트 루프인데 시작=끝 프레임의 조명·그림자가 미세하게 어긋남** → 반복 재생 시 이음매에서 튄다.
- **오디오 기반 전환(J컷/L컷/스팅어 컷 등)을 순수 시각 모델에서 완전 재현 가능하다고 기대** → 시각적 근사만 가능하다는 걸 미리 알린다.
