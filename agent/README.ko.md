# 에이전트 인프라 스킬

[English version](README.md)

에이전트가 직접 일하는 대신 **다른 에이전트를 부리도록** 하는 스킬 모음입니다.
`design/`이 한 세션 안에서 역할을 나누는 파이프라인이라면, 이쪽은 프로세스 경계를
넘습니다 — 별도 터미널 pane에 워커 에이전트를 띄우고, 브리핑하고, 감시하고,
결과물을 회수합니다.

---

## 핵심 원칙

1. **오케스트레이터는 코드를 만지지 않는다.** 직접 파일을 고치기 시작하는 순간
   워커를 감시할 수 없게 됩니다. 위임과 실행은 다른 일입니다.
2. **워커는 맥락 없이 시작한다.** 워커는 대개 다른 벤더의 에이전트라 이 프로젝트의
   `CLAUDE.md`도 `.claude/skills/`도 읽지 못합니다. 필요한 건 전부 프롬프트에
   인라인으로 넣어야 합니다.
3. **상태는 완료의 증거가 아니다.** 워커가 `idle`이라는 건 끝났다는 뜻일 수도,
   죽었다는 뜻일 수도 있습니다. 완료는 디스크에 결과 파일이 있는 것으로만
   증명되고, 터미널 상태로는 절대 증명되지 않습니다.
4. **회수는 터미널보다 오래 살아남아야 한다.** 풀스크린 에이전트는 alternate
   screen에 렌더링해서 scrollback에 아무것도 남기지 않습니다. 그래서 결과는 화면에서
   읽지 않고 파일로 씁니다.
5. **여기는 정책, 문법은 딴 데.** 이 스킬들은 무엇이 허용되는지를 정합니다.
   어떻게 쓰는지는 CLI의 `--help` 출력이 권위입니다.

---

## 스킬

### `herdr-orchestrate` — herdr pane 기반 병렬 위임

**목적**: 요청을 독립 단위로 쪼개고, 단위마다 워커 에이전트를 자기 몫의
[herdr](https://github.com/wooobo/herdr) pane에 띄우고, 각자에게 필요한 맥락으로
브리핑하고, 돌아가는 동안 승인 프롬프트를 처리하고, 결과를 모아 보고합니다.

**요구사항**: `HERDR_ENV=1` — 워커 자리를 만들려고 호출자 자신의 pane을 분할하기
때문에 반드시 herdr pane 안에서 실행해야 합니다.

**입력**: 작업 설명. 선택적으로 프로젝트 설정 `.claude/orchestrator/registry.md`
(대상 레지스트리)와 `.claude/orchestrator/rules.md`(프로젝트 규칙). 없으면 현재
저장소를 대상으로 하는 범용 모드로 동작합니다.

**출력**: 워커별 마크다운 결과 파일 하나씩(각 워커 자신의 작업 디렉토리 안에 작성),
그리고 각 워커의 "확인 필요" 항목을 전면에 드러낸 통합 보고.

**이럴 때 사용**:

- 여러 저장소나 여러 독립 작업을 동시에 굴려야 할 때
- 다른 벤더의 모델에게 같은 작업을 교차 검증시킬 때
- 오래 걸리는 작업을 백그라운드 pane으로 넘기고 세션은 계속할 때

**이럴 땐 사용 금지**:

- 파일 몇 개 읽기, 한 파일 수정, 5분 안에 끝날 작업. 워커 스폰 비용이 더 큽니다
- 서로 다른 디렉토리를 소유하는 단위로 쪼갤 수 없는 작업

**트리거 표현**: "병렬로", "따로 띄워서", "코덱스한테 시켜", "워커 붙여",
"백그라운드로 돌려", "A랑 B 같이 작업", "fan out", "second opinion", "교차 검증".

**강제 규칙**:

- 작업 디렉토리 하나당 워커 하나. 한 디렉토리에 둘을 붙이면 서로 파일을 망칩니다
- 호출자 pane은 절대 쪼개지 않습니다. 워커는 전용 탭에 격자로 들어갑니다 —
  2개는 나란히, 3개도 나란히, 4개는 2×2, 5개는 2/2/1, 6개는 3×2. 7번째는 새 탭이라
  기하가 더 이상 인원을 제한하지 않습니다
- 격자는 첫 스폰 때 한 번에 다 쪼갭니다. `--total`이 필요한 이유입니다. 필요할 때마다
  쪼개면 하필 승인 다이얼로그를 띄운 워커를 리사이즈하게 되고, 읽는 도중의 리드로는
  그 워커를 감시할 유일한 통로를 끊습니다
- 워커 탭은 화면에 안 보입니다. 최종 보고에 반드시 올려야 하고, 안 그러면 잊힌 채
  계속 돌아갑니다
- 결과 파일은 워커 자신의 디렉토리 안에 둡니다. 워크스페이스로 샌드박스된 워커는
  그 밖에 쓸 수 없고, 브리핑도 그걸 금지하고 있습니다
- 워커는 커밋하지 않습니다. 커밋·푸시·브랜치 생성·새 의존성·중첩 에이전트 스폰
  승인 요청은 거부합니다
- 오케스트레이터가 만들지 않은 pane은 닫지 않습니다

## 디렉토리

```text
agent/
├── README.md
├── README.ko.md
└── herdr-orchestrate/
    ├── SKILL.md                  정책과 0~5단계 흐름
    ├── scripts/
    │   └── orchestrate.mjs       spawn / prompt / unstick / status / collect
    └── reference/
        ├── briefing.md           맥락 없는 워커에게 무엇을 말할지
        ├── gotchas.md            누적 실패 기록 (유일하게 쓰기가 일어나는 파일)
        └── kinds/
            ├── codex.md          codex 승인 판단과 함정
            └── claude.md         claude 워커 조작, alternate screen 문제
```

`SKILL.md`만 항상 컨텍스트에 올라갑니다. `reference/` 아래는 필요할 때만 읽습니다 —
`briefing.md`는 프롬프트를 조립할 때, `kinds/<kind>.md`는 워커가 blocked 되거나
이상하게 굴 때, `gotchas.md`는 매 실행 시작 시점에.

## 무엇이 코드고 무엇이 산문인가

분할선은 파일 단위가 아니라 작업 한가운데를 지나갑니다:

| 관심사 | 소유자 | 이유 |
| --- | --- | --- |
| 벤더별 스폰 플래그 | `orchestrate.mjs` | 순수 데이터. "이 플래그 빼먹지 마라"는 경고가 필요한 문서는 애초에 함수였어야 합니다. |
| pane 분할 방향과 크기 하한 | `orchestrate.mjs` | 산술 계산 + 80x20 미만이면 거부. 판독 불가능한 pane은 감시 불가능한 워커를 만듭니다. |
| 결과 경로와 회수 계약 | `orchestrate.mjs` | 매번 같은 규칙으로 계산되는데, 손으로 조립했을 때 실제로 틀렸습니다. |
| 워커→cwd→pane 매핑 | `orchestrate.mjs` (manifest) | 상태는 모델 컨텍스트보다 오래 살아야 합니다. 20분 대기가 이걸 잃게 만들면 안 됩니다. |
| 워커의 요청을 승인할지 | `SKILL.md` + `kinds/` | 임의의 명령 문자열에 대한 의미 판단. 스크립트는 UI가 어떤 키를 원하는지는 알아도, 그 명령을 실행해도 되는지는 모릅니다. |
| 워커가 알아야 할 것 | `briefing.md` | 안목이 필요한 압축. "모르면 틀리는 것만"이라는 기준은 함수 시그니처로 표현되지 않습니다. |

스크립트는 절벽에서 떨어집니다 — 패턴이 안 맞으면 호출자에게 정책이 하나도 남지
않습니다. 산문은 완만하게 나빠집니다 — 표에 없는 화면 문구를 만나도 원칙이 남아 있고
사용자에게 넘길 통로가 있습니다. 그래서 **벤더가 새 TUI를 내면 바뀌는 것은 산문으로,
매번 똑같은 것은 코드로** 갑니다.
